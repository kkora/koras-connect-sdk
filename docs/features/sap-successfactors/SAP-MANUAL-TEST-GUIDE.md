# SAP SuccessFactors manual test guide

[Feature tracker](../README.md) | [Category](README.md)

A human-executable test script for the SAP SuccessFactors connector: a sample walkthrough a tester can run today
with zero credentials, plus a numbered QA test-case list a tester records pass/fail against. This complements, not
replaces, the automated suite in `tests/Koras.Connect.Tests/Sap/` — those run in CI; this document is for a person
manually confirming the same behavior by eye before a release. This document is not itself an automated test.

## Part 1 — Offline sample walkthrough

Every command below runs fully offline against a synthetic `HttpMessageHandler`; none contact a live SAP
SuccessFactors tenant, and none require credentials, a company id or a SAML assertion provider. Run every sample
once before starting Part 2; a failure here means do not proceed to sandbox testing.

```
dotnet build Koras.Connect.slnx -c Release
dotnet run --project samples/SuccessFactors.Diagnostics
dotnet run --project samples/SuccessFactors.PersonAndEmploymentSync
dotnet run --project samples/SuccessFactors.FoundationObjects
dotnet run --project samples/SuccessFactors.IncrementalSync
dotnet run --project samples/SuccessFactors.EmploymentWrites
```

| Sample | Demonstrates |
|---|---|
| `SuccessFactors.Diagnostics` | `SuccessFactorsClient.EnumeratePersonsAsync` classifying HTTP 401/403/429/503 into `AuthenticationException`/`AuthorizationException`/`ThrottleException`/`TransportException` rather than leaking a raw status; a pre-canceled read propagating as `OperationCanceledException` without reclassification; and `SapODataError.TryParseSanitizedCode` extracting only the safe `error.code` field from a captured error body (never `error.message.value`), including its `null`-returning behavior on malformed input (SAP-005). |
| `SuccessFactors.PersonAndEmploymentSync` | The end-to-end read/write surface: `SamlBearerTokenSource` exchanging a SAML2-bearer assertion for an OAuth token; `EnumeratePersonsAsync`/`EnumerateEmploymentAsync`/`EnumerateJobsAsync` against `PerPerson`/`EmpEmployment`/`EmpJob`; `ResolveManagerChainAsync` walking a manager chain one hop at a time; `GetMetadataAsync` plus `SuccessFactorsClient.ParseEntityDescriptors` parsing `$metadata`; and an opt-in `UpsertAsync("PerPerson", ..., writesEnabled: true)` call (SAP-001/SAP-002/SAP-003/SAP-011/SAP-014). |
| `SuccessFactors.FoundationObjects` | `EnumerateFoundationObjectAsync<T>` reading `FODepartment`/`FODivision`/`FOLocation`, and `ResolveDepartmentParentChainAsync` walking a department's `parentExternalCode` chain to its root using the same visited-set cycle guard as `ResolveManagerChainAsync` (throws `InvalidDataException` on a revisited code) (SAP-010). Note: the sample's own comments flag the foundation-object entity-set names and fields as confirmed only against the documented API reference, not yet against a live tenant's `$metadata` — see "Not yet implemented" in the connector's README. |
| `SuccessFactors.IncrementalSync` | `SapDeltaFilters.BuildFilter` building a checkpointed `$filter` from a `SapDeltaCheckpoint` with a clock-skew overlap window; `SapDeltaSync.RunAsync` composing `EnumerateEmploymentAsync` with `Reconciliation.DetectChangesAsync` against a caller-supplied fingerprint dictionary, correctly reporting one new record and treating the unchanged record as unchanged by its SHA-256 fingerprint; and the checkpoint only ever advancing after the full scan completes without throwing (SAP-013). |
| `SuccessFactors.EmploymentWrites` | The opt-in `writesEnabled: true` upsert surface: the generic `UpsertAsync` primitive versus the typed `UpsertEmploymentAsync`/`UpsertJobAsync` wrappers, which reject a row missing its documented composite key (`userId`+`startDate` for `EmpEmployment`, `userId`+`seqNumber` for `EmpJob`) locally with an `ArgumentException` before any HTTP call; and a read-only-entity row arriving as HTTP 200 with a per-row `Succeeded = false` failure, demonstrating that every `UpsertResult` must be inspected individually rather than inferring success from the outer HTTP status (SAP-003/SAP-012). |

## Part 2 — Manual QA test-case script

Record a result (Pass/Fail/Blocked) and the date for each row. "Preconditions" beyond a clean checkout and
`dotnet build` are called out per case.

| Case | Area | Preconditions | Steps | Expected result |
|---|---|---|---|---|
| TC-SAP-01 | Error classification and diagnostics (offline) | none | Run `dotnet run --project samples/SuccessFactors.Diagnostics`. | Each of HTTP 401/403/429/503 prints as `AuthenticationException`/`AuthorizationException`/`ThrottleException`/`TransportException` respectively; the pre-canceled read reports `OperationCanceledException` without contacting the handler; `SapODataError.TryParseSanitizedCode` prints `COE0027` extracted from the sample error body and `(null)` for malformed input, never the `message.value` tenant-specific text. |
| TC-SAP-02 | Person/employment/job read, manager chain, metadata, upsert (offline) | none | Run `dotnet run --project samples/SuccessFactors.PersonAndEmploymentSync`. | A SAML-bearer token is acquired; one person, one employment record and one job record print; the manager chain for `sample-1` resolves with the configured length; `$metadata` parses to report the one modeled `PerPerson` entity type; the opt-in upsert prints `editStatus=UPDATED, succeeded=True`. |
| TC-SAP-03 | Foundation objects and department parent chain (offline) | none | Run `dotnet run --project samples/SuccessFactors.FoundationObjects`. | Departments, divisions and locations print with their `externalCode`/`status`; the department parent chain for `DEPT-ENGINEERING` resolves to `DEPT-ROOT` with no infinite loop. |
| TC-SAP-04 | Delta/incremental sync (offline) | none | Run `dotnet run --project samples/SuccessFactors.IncrementalSync`. | The checkpointed `$filter` string prints; exactly one changed record (`sample-1`) is detected while `sample-2` (matching fingerprint) is excluded; the checkpoint advances from the configured start time to the latest observed `lastModifiedDateTime`. |
| TC-SAP-05 | Typed upsert validation (offline) | none | Run `dotnet run --project samples/SuccessFactors.EmploymentWrites`. | The generic `UpsertAsync` call succeeds; `UpsertEmploymentAsync` and `UpsertJobAsync` each throw `ArgumentException` locally for a row missing its composite key before any HTTP call, then succeed once the key is present; the read-only-entity row reports `succeeded=False` at `httpCode=403` despite the outer call completing, and its detailed message is not printed by the sample's unqualified `ToString()` call. |
| TC-SAP-06 | Automated regression complement | none | Run `dotnet test tests/Koras.Connect.Tests/Koras.Connect.Tests.csproj --filter FullyQualifiedName~Sap`. | All SAP-scoped tests (`SapAuthenticationTests`, `SapClientExpansionTests`, `SapDeltaSyncTests`, `SapEmploymentAndJobTests`, `SapExceptionClassificationTests`, `SapFoundationObjectTests`, `SapManagerResolutionTests`, `SapMappingTests`, `SapMetadataTests`, `SapSecretCanaryTests`, `SapServiceCollectionTests`) pass; none are skipped (there is no sandbox-gated SAP test today, unlike the two skipped `AdpSandboxTests` cases in the ADP suite). |
| TC-SAP-07 **(Sandbox)** | Live person/employment/job read | Authorized SAP SuccessFactors sandbox/test tenant; proposed `KORAS_SAP_SANDBOX_*` settings below configured locally (environment variable, user-secret, or `appsettings.local.json`, following the `SandboxConfiguration` precedent in `tests/Koras.Connect.Tests/Sdk/SandboxConfiguration.cs` — these names are a proposed convention only and are not read by any code in this repository today). | Write a small throwaway console program (adapt `samples/SuccessFactors.PersonAndEmploymentSync/Program.cs`): replace the synthetic `HttpMessageHandler` with a real `HttpClient` pointed at `KORAS_SAP_SANDBOX_ODATA_ROOT`; construct `SamlBearerTokenSource` with `KORAS_SAP_SANDBOX_TOKEN_ENDPOINT`, `KORAS_SAP_SANDBOX_COMPANY_ID`, `KORAS_SAP_SANDBOX_CLIENT_ID`, and a delegate that returns a real fresh SAML2 assertion from your IdP (or whatever OAuth client-credential exchange your tenant's IdP actually issues as that assertion's source — this SDK only implements the SAML2-bearer grant exchange itself, via `SamlBearerTokenSource`); call `EnumeratePersonsAsync`/`EnumerateEmploymentAsync`/`EnumerateJobsAsync` filtered to one authorized test person, `KORAS_SAP_SANDBOX_PERSON_ID`. | Exactly the one authorized person/employment/job record returns; no `AuthenticationException`/`AuthorizationException` is thrown; no unrelated person's data is returned. Record the tenant, entity set and HTTP status observed. Delete the throwaway program or its credentials from disk afterward. |
| TC-SAP-08 **(Sandbox)** | Live delta/incremental sync pass | Same settings as TC-SAP-07, plus `KORAS_SAP_SANDBOX_DELTA_START` (an ISO-8601 timestamp safely in the past for the test tenant). | Adapt `samples/SuccessFactors.IncrementalSync/Program.cs` the same way: real `HttpClient`/`SamlBearerTokenSource` as above, a `SapDeltaCheckpoint` seeded from `KORAS_SAP_SANDBOX_DELTA_START`, and `SapDeltaSync.RunAsync` against `EnumerateEmploymentAsync` with an empty `previousFingerprints` dictionary for the first pass. Run it twice in a row without any tenant change in between. | First pass returns every `EmpEmployment` record modified since the seed time as "changed" and returns an advanced checkpoint. Second pass, seeded from the first pass's advanced checkpoint and its fingerprints, returns zero changes (assuming no real tenant write occurred between passes). Record the entity count and the two checkpoint values observed. |
| TC-SAP-09 **(Sandbox)** | Live upsert with explicit cleanup | Same settings as TC-SAP-07, plus `KORAS_SAP_SANDBOX_WRITE_PERSON_ID` naming a disposable test person/record your tenant's technical user is explicitly authorized to write (never a production or shared-use record), and a recorded plan to restore or delete the change after the run. | Adapt `samples/SuccessFactors.EmploymentWrites/Program.cs`: real `HttpClient`/`SamlBearerTokenSource`, then call `UpsertAsync`/`UpsertEmploymentAsync`/`UpsertJobAsync` with `writesEnabled: true` against `KORAS_SAP_SANDBOX_WRITE_PERSON_ID` only. Inspect every returned `UpsertResult.Succeeded` individually — per the root README and the `SuccessFactors.EmploymentWrites` sample, a 200-level HTTP response can still carry a row-level failure, so a non-exceptional call is not sufficient evidence of success. | Each returned `UpsertResult.Succeeded` is `true` and its `EditStatus` matches the intended change (for example `UPDATED`); any row with `Succeeded = false` is treated as a failure regardless of HTTP status. Immediately after recording the result, execute the recorded cleanup/restore step against the test tenant and confirm (via a follow-up read) that the disposable record is back in its prior state. |

The Sandbox cases above are a genuinely manual, ad hoc procedure today, not an automated opt-in test suite: unlike
`tests/Koras.Connect.Tests/Adp/AdpSandboxTests.cs`, there is no `tests/Koras.Connect.Tests/Sap/*Sandbox*` test file, no
`[Fact(Skip = "...")]`-gated SAP sandbox test to un-skip, and no code in this repository that reads any
`KORAS_SAP_SANDBOX_*` variable — every name used above is a proposed convention for a tester's own throwaway script,
consistent with the `SandboxConfiguration` precedent, not a wired-up harness.
